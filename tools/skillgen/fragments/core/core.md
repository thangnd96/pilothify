# /pilothify

Turn any folder of files into a navigable knowledge graph with community detection, an honest audit trail, and three outputs: interactive HTML, GraphRAG-ready JSON, and a plain-language GRAPH_REPORT.md.

## Usage

```
/pilothify                                             # full pipeline on current directory (HTML viz; add --obsidian for a vault)
/pilothify <path>                                      # full pipeline on specific path
/pilothify https://github.com/<owner>/<repo>           # clone repo then run full pipeline on it
/pilothify https://github.com/<owner>/<repo> --branch <branch>  # clone a specific branch
/pilothify <url1> <url2> ...                           # clone multiple repos, build each, merge into one cross-repo graph
/pilothify <path> --mode deep                          # thorough extraction, richer INFERRED edges
/pilothify <path> --update                             # incremental - re-extract only new/changed files
/pilothify <path> --force                              # full rebuild allowing graph shrink (e.g. after deleting files)
/pilothify <path> --directed                            # build directed graph (preserves edge direction: source→target)
/pilothify <path> --whisper-model medium                # use a larger Whisper model for better transcription accuracy
/pilothify <path> --cluster-only                       # rerun clustering on existing graph
/pilothify <path> --no-viz                             # skip visualization, just report + JSON
/pilothify <path> --html                               # (HTML is generated by default - this flag is a no-op)
/pilothify <path> --svg                                # also export graph.svg (embeds in Notion, GitHub)
/pilothify <path> --graphml                            # export graph.graphml (Gephi, yEd)
/pilothify <path> --neo4j                              # generate pilothify-out/cypher.txt for Neo4j
/pilothify <path> --neo4j-push bolt://localhost:7687   # push directly to Neo4j
/pilothify <path> --falkordb                           # generate pilothify-out/cypher.txt for FalkorDB
/pilothify <path> --falkordb-push falkordb://localhost:6379   # push directly to FalkorDB
/pilothify <path> --mcp                                # start MCP stdio server for agent access
/pilothify <path> --watch                              # watch folder, auto-rebuild on code changes (no LLM needed)
/pilothify <path> --wiki                               # build agent-crawlable wiki (index.md + one article per community)
/pilothify <path> --obsidian --obsidian-dir ~/vaults/my-project  # write vault to custom path (e.g. existing vault)
/pilothify add <url>                                   # fetch URL, save to ./raw, update graph
/pilothify add <url> --author "Name"                   # tag who wrote it
/pilothify add <url> --contributor "Name"              # tag who added it to the corpus
/pilothify query "<question>"                          # BFS traversal - broad context
/pilothify query "<question>" --dfs                    # DFS - trace a specific path
/pilothify query "<question>" --budget 1500            # cap answer at N tokens
/pilothify path "AuthModule" "Database"                # shortest path between two concepts
/pilothify explain "SwinTransformer"                   # plain-language explanation of a node
```

## What pilothify is for

Drop any folder of code, docs, papers, images, or video into pilothify and get a queryable knowledge graph. Persistent across sessions, honest audit trail (EXTRACTED/INFERRED/AMBIGUOUS), community detection surfaces cross-document connections you wouldn't think to ask about.

**When a graph is worth building:** this applies when you are choosing a tool yourself; if the user invoked `/pilothify`, follow that request as asked. AST extraction of code is fast and free, but semantic extraction of docs, papers and images runs the model over every file, which can cost minutes and tens of thousands of tokens.

If a graph already exists, query it. With no graph, one targeted lookup ("where is X defined", "what calls Y" in an ordinary-sized codebase) is faster and free with a plain text search such as `grep` and `Read`: search directly instead of running the steps below, and mention that a graph can be built if the user wants one. Build one when you expect many questions against this corpus, the corpus is large or unfamiliar, the question needs links text search cannot see (doc to code, across documents), or it is structural (communities, bridges, import cycles).

### Step 3 - Extract entities and relationships

This step has two parts: **structural extraction** (deterministic, free) and **semantic extraction** (LLM, costs tokens).

> **pilothify needs no API key. **Step B1 - Split into chunks**

Load files from `pilothify-out/.pilothify_uncached.txt`. Split into chunks bounded by BOTH limits: at most 20-25 files AND at most ~6000 total lines per chunk. A text file longer than 2000 lines gets a chunk to itself - that is past the Read tool's single-call cap, so sharing a chunk with other files guarantees it is only partly read. Each image gets its own chunk (vision needs separate context). When splitting, group files from the same directory together so related artifacts land in the same chunk and cross-file relationships are more likely to be extracted.

Both bounds matter. The line bound is not only about the 2000-line Read cap: a subagent holding 25 files splits its attention across all of them and skims the dense ones, and a 590-line plan can come back with zero nodes that way. Bounding content as well as file count is what keeps a chunk's coverage honest.

**Step B3.5 - Verify each reported file was actually read to its end**

A subagent that only read the first Read call's worth of a long file still writes a well-formed chunk, so "chunk file exists and parses" is not evidence of coverage. Compare each file's self-reported `coverage` against its real length:

```bash
$(cat pilothify-out/.pilothify_python) -c "
import json, glob
from pathlib import Path

INPUT_PATH = Path('pilothify-out/.pilothify_root').read_text(encoding=\"utf-8-sig\").strip()
covered = {}
for c in sorted(glob.glob('pilothify-out/.pilothify_chunk_*.json')):
    d = json.loads(Path(c).read_text(encoding=\"utf-8\"))
    for src, n in (d.get('coverage') or {}).items():
        covered[src] = max(covered.get(src, 0), int(n))

partial = []
for src, n in sorted(covered.items()):
    p = Path(src)
    if not p.is_absolute():
        p = Path(INPUT_PATH) / src
    if not p.is_file():
        continue
    total = p.read_bytes().count(b'\n')  # like wc -l: an unterminated last line is not short
    if total and n < total:
        partial.append((src, n, total))

Path('pilothify-out/.pilothify_partial.txt').write_text('\n'.join(s for s, _, _ in partial), encoding=\"utf-8\")
if partial:
    print(f'WARNING: {len(partial)} file(s) were only partly read. They are cached as partial and retried on the next --update:')
    for src, n, total in partial:
        print(f'  {src}: read {n} of {total} lines')
else:
    print('Coverage OK - every file a subagent reported was read to its last line')
"
```

Tell the user which files came up short and what was lost (the line counts are printed above). The nodes already extracted for those files are kept - they are still true - but the file is cached as partial and left unstamped in the manifest below, so the next `--update` re-dispatches it and replace-on-re-extract swaps the partial node set for a complete one. A file a subagent did not report at all is not counted as partial - there is nothing to compare against - which is why the prompt rule in `references/extraction-spec.md` asks for the count in the first place.

#### Part C - Merge AST + semantic into final extraction

```bash
$(cat pilothify-out/.pilothify_python) -c "
import sys, json
from pathlib import Path

ast = json.loads(Path('pilothify-out/.pilothify_ast.json').read_text(encoding=\"utf-8\"))
sem = json.loads(Path('pilothify-out/.pilothify_semantic.json').read_text(encoding=\"utf-8\"))

for n in sem['nodes']:
    n.setdefault('_origin', 'semantic')
for e in sem['edges']:
    e.setdefault('_origin', 'semantic')

# Merge: AST nodes first, semantic nodes deduplicated by id
seen = {n['id'] for n in ast['nodes']}
merged_nodes = list(ast['nodes'])
for n in sem['nodes']:
    if n['id'] not in seen:
        merged_nodes.append(n)
        seen.add(n['id'])

merged_edges = ast['edges'] + sem['edges']
merged_hyperedges = sem.get('hyperedges', [])
merged = {
    'nodes': merged_nodes,
    'edges': merged_edges,
    'hyperedges': merged_hyperedges,
    'input_tokens': sem.get('input_tokens', 0),
    'output_tokens': sem.get('output_tokens', 0),
}
Path('pilothify-out/.pilothify_extract.json').write_text(json.dumps(merged, indent=2, ensure_ascii=False), encoding=\"utf-8\")
total = len(merged_nodes)
edges = len(merged_edges)
print(f'Merged: {total} nodes, {edges} edges ({len(ast[\"nodes\"])} AST + {len(sem[\"nodes\"])} semantic)')
"
```

### Step 4 - Build graph, cluster, analyze, generate outputs

**Before starting:** the code blocks below pass `directed=IS_DIRECTED` to `build_from_json()` and `force=IS_FORCE` to `to_json()`.
